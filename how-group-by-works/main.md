## Как устроены агрегатные функции

Вначале вспомним, что такое агрегатная функция.

Агрегатная функция - это функция, вычисляющая результат на множестве данных.

> Слайд: эти 2 запроса

Например,

```sql
-- Самый большой возрасти среди всех пользователей
SELECT max(age) FROM users;

-- Среднее количество денежных переводов каждого пользователя
SELECT userid, avg(transferred) FROM user_transactions GROUP BY userid;
```

Агрегирующие функции бывают разные и у всех разное поведение.
Например, `max` мы можем рассчитывать налету, храня только 1 число (самое большое значение), а вот для эффективного расчета `avg` придется хранить 2 числа - сумма и количество, но при этом возвращаемое значение это 1 число, которое вычисляется из этих 2-ух.

> Слайд: псевдокод ниже

Чтобы поддерживать такие различные свойства был разработан свой протокол работы с агрегатами.
Визуализировать его можно так:

```python
# Инициализация состояния
state = init()

# Применение функции перехода
for tuple in input:
   state = transit(state, tuple)

# Подсчет результата
result = finalize(state)
```

1. Инициализируем состояние
2. Для каждого кортежа из входа применяем функцию перехода
3. Вызываем финализатор, подсчитывающий результат

> Слайд: create aggregate ниже

Есть много встроенных агрегатных функций, но можно создать и свои. Сделать это можно с помощью `CREATE AGGREGATE`. У нее много аргументов, но мы сконцентрируемся на главных:

```sql
CREATE AGGREGATE some_agg(a int, b int) (
   -- Начальное состояние
   initcond  = '(0,0)'
   -- Функция перехода
   sfunc     = average_transition,
   -- Финализатор
   finalfunc = average_final,
)
```

- `initcond` - изначальное значение агрегата
- `sfunc` - функция перехода
- `finalfunc` - финализатор

> Слайд: запрос и его результат на слайде

Для встроенных агрегатов мы можем посмотреть из чего они сделаны.
Все агрегаты хранятся в таблице pg_aggregate и вот небольшая часть его содержимого.

```sql
select aggfnoid, agginitval, aggtransfn, aggfinalfn from pg_aggregate;

         aggfnoid       |    agginitval   |    aggtransfn    |      aggfinalfn              
------------------------+-----------------+------------------+-----------------------
 pg_catalog.stddev      | {0,0,0}         | float4_accum     | float8_stddev_samp
 pg_catalog.avg         | {0,0,0}         | float4_accum     | float8_avg
 pg_catalog.avg         | {0,0}           | int4_avg_accum   | int8_avg
 pg_catalog.max         |                 | int4larger       | -
 pg_catalog.max         |                 | float4larger     | -
 
```

Из-за поддержки перегрузки агрегат с 1 имененем может работать с разными типами.
Главные моменты мы можем увидеть:

- `avg` для `int4` в initcond - 2 нуля (сумма и количество), функция перехода `int4_avg_accum` - увеличивает количество и сумму, а `int8_avg` финализатор - делит их.
- `max` для `double` не имеет финализатора и его состояние описывается одним числом

С помощью этих 3 вещей мы можем описать практически любую агрегирующую функцию.

Но агрегирующие функции лишь часть общей картины под названием группировка, о которой мы сегодня и поговорим.

## Простая агрегация

> Слайд: запрос и вывод ниже

Для начала рассмотрим самый простой случай - плоская группировка.

В оригинале его называются plain aggregate, а сам узел в плане отображается просто как Aggregate, но я не смог найти более подходящее название.

Логика узла группировки располагается в файле `nodeAgg.c`.

Сама плоская группировка - это группировка по всем данным, т.е. мы не указываем `GROUP BY`.
В узле она отображается просто как `Aggregate`.

```sql
EXPLAIN SELECT avg(a) FROM tbl;
                         QUERY PLAN                          
-------------------------------------------------------------
 Aggregate  (cost=35.50..35.51 rows=1 width=8)
   ->  Seq Scan on tbl  (cost=0.00..30.40 rows=2040 width=4)
(2 rows)
```

Нам не нужно предобрабатывать входные данные. Просто получаем на вход кортеж и отдаем функции перехода.
Разберем как это работает.

> Слайд: `ExecAgg` + `AggStrategy`

Вы уже знаете, что PostgreSQL умеет группировать несколькими стратегиями.
Каждая из них описана перечислением `AggStrategy`.

За выполнение узла группировки отвечает функция `ExecAgg`, внутри которой простой switch определяющий нужную стратегию.

За плоскую группировку отвечает `AGG_PLAIN` и для выполнения используем `agg_retrieve_direct`.
Остальные мы рассмотрим потом.

> Слайд: упрощенный код `agg_retrieve_direct` выделен fetch_input_tuple

Внутри нас ждет обычный `while` цикл проходящий по всем кортежам из входа и передающий их функции перехода. PostgreSQL работает по итераторной модели и каждый раз возвращает по 1 кортежу из подузла. Если вернул `NULL`, то значит данных больше нет.

Вначале нам нужно получить сами данные, то есть кортежи для агрегирования.
Это мы делаем с помощью функции `fetch_input_tuple`. Пока нам не важно что внутри, но поверьте на слово, что они читаются из под-узла, например, `SeqScan`.

> Слайд: код agg_retrieve_direct выделен initialize_aggregates

После того как мы получили кортеж, то знаем, что как минимум 1 группа, но будет.
Поэтому можем инициализировать агрегаты.

> Слайд: `initialize_aggregates` цикл простой

Выполняется это с помощью функции `initialize_aggregates`. Чтобы понять, что происходит разберем основные компоненты логики агрегации.

> Слайд: схема с инициализацией, где AggStatePerGroup - `init-scheme`

`AggStatePerGroup` представляет само состояние агрегата, которое используется для функции перехода.
Оно создается для каждой группы, т.е. набора конкретных значений атрибутов группировки.

Для AVG состояние - это пара из 2 чисел - сумма и количество.

Можете заметить, что здесь не 2 поля: значение и NULL, а 3 - флаг `noTransValue`.

Проблема следующая - если изначальное состояние агрегата NULL, то первое не NULL значение становится этим состоянием, но если мы используем только 1 флаг - как мы различим NULL, который еще не выставлен от NULL, который вернула функция перехода. Для решения мы задействуем дополнительный флаг.

> Слайд: схема с PerTrans (`trans-final-scheme`)

Само начальное состояние мы берем из `AggStatePerTrans`. Кроме того, эта же структура содержит информацию и для функции перехода.

Но вот финализация выделена в отдельную структуру - `AggStatePerAgg`.

И опять вопрос - зачем. А все дело в оптимизации.


Эта идея и легла в основу такой оптимизации.

Возвращаемся обратно и теперь логика инициализации становится понятна.
Из `AggStatePerTrans` мы берем наше состояние и инициализируем `AggStatePerGroup`: само значение и 2 флага.

> Слайд: `agg_retrieve_direct` около `advance_aggregates`

Теперь нам необходимо эту самую функцию перехода применить. Делается это в функции `advance_aggregates`.

Но там не будет напрямую вызываться код функции перехода. Многие выражения в PostgreSQL выполняются не как отдельные функции, а преобразовываются в последовательность команд для выполнения.

> Слайд: `ExecInterpExpr`, но только те шаги, которые нужны мне

Для того, чтобы вызвать функцию перехода нам нужно только получить значение из кортежа (команда `OUTER_FETCHSOME`) и вызвать саму функцию перехода (`AGG_PLAIN_TRANS_BYVAL`).

Проваливаемся внутрь и видим непосредственный вызов функции перехода - `int4_sum`.
Так как это наше первое значение, то состояния нет и само число становится нашим новым состоянием - `1`.

Так как у нас только 1 агрегат, то на этом мы останавливаемся и возвращаемся обратно.

> Слайд: `agg_retrieve_direct` выделен fetch_input_tuple + break

По возвращении мы повторяем чтение и применение функции агрегации пока не достигнем конца.

> Слайд: `agg_retrieve_direct` выделен finalize_aggregates

Когда вход закончился, то применяем финализатор.

> Слайд: `finalize_aggregate`, но только применение финализатора + скриншот отладчика с вызовом

Это делается в функции `finalize_aggregate`.
Финализатор для `avg` - это `int8_avg`, который сейчас и вызывается.

## Группировка по столбцам

> Слайд: запрос с GROUP BY ниже

```sql
SELECT a, avg(b) FROM tbl GROUP BY a;

                       QUERY PLAN                        
---------------------------------------------------------
 HashAggregate
   Group Key: a
   ->  Seq Scan on tbl

SELECT a, b, c FROM tbl GROUP BY a, b, c;

                           QUERY PLAN                           
----------------------------------------------------------------
 Group  (cost=1.08..1.12 rows=3 width=12)
   Group Key: a, b, c
   ->  Sort  (cost=1.08..1.09 rows=4 width=12)
         Sort Key: a, b, c
         ->  Seq Scan on tbl  (cost=0.00..1.04 rows=4 width=12)
```

К этому моменту мы разобрали то, как работают функции агрегации и плоская группировка, но основная доля работы на группировке по атрибутам.

Для этого в SQL используется конструкция `GROUP BY`, в которой передается список из элементов группировки.
Postgres поддерживает 2 стратегии группировки: хэширование и сортировка.

Первое, нам нужно понять как хэшировать атрибуты.

В PostgreSQL можно выделить 4 типа типа: базовый, диапазон, перечисление и составной.

Чтобы захэшировать диапазон - хэшируем начало и конец (`hash_range`), перечисление - само числовое представление (`hashenum`), а для составного типа (`hash_record`) - каждый из его членов.
Поэтому если мы умеем хэшировать базовый, то и все остальные. Но если вы создавали тип через `CREATE TYPE`, то могли заметить, что там не указывается функция хэширования.

> Слайд: запрос и результат

```sql
select ap.amproc
   from pg_opfamily f
      join pg_am a on f.opfmethod = a.oid
      join pg_amproc ap on ap.amprocfamily = f.oid
where a.amname = 'hash'
  and ap.amproclefttype = 'int4'::regtype
  and ap.amprocnum = 1;

  amproc  
----------
 hashint4
(1 row)
```

Мы используем системный каталог. В частности, нам нужно посмотреть на HASH индекс.
Про инфраструктуру семейства и классов операторов говорить не буду. Просто скажу, что функция хэширования для типа хранится как support функция под номером 1.
Что сейчас мы и ищем.

Для int это `hashint4`.

Откуда взять функцию хэширования разобрались и осталась главная проблема - нехватка памяти.

Для каждого узла задается его мягкий предел использования памяти - `work_mem`. И его превышение необходимо обработать.
Чтобы решить эту задачу используется знание о механизме работы хэш-таблицы.

> Слайд: хэш-таблица, от нее отходят стрелки с партициями, а в ней PerGroup с хэш-значениями

Верхнеуровнево, хэш-таблицу можно представить как массив, разбитый на партиции. В каждой партиции лежат элементы, хэши которых равны (по определенной маске).
То есть для поиска или вставки нам нужно вычислить хэш, применить к нему маску и получить индекс партиции, а затем пройтись по нему и уже выполнить непосредственное сравнение элементов.
Но когда мы начинаем сбрасывать кортежи, то уже существующие элементы останутся в таблице, поэтому мы, грубо говоря, начнем строить новую, но уже из сброшенных кортежей.

Из этого исходит следующая идея: сделаем партиции на столько маленькими, что каждая сможет полностью помещаться в памяти.
Тогда, в лучшем случае, эта стратегия позволит нам обойтись только 1 сбросом на диск.

Теперь как это решить. Нам дано: оценка планировщика количества групп, размер 1 кортежа и доступный размер памяти.
Но нам не известно распределение данных, поэтому мы предполагаем, что оно равномерное, а значит и хэш-значения тоже будут распределены равномерно и в каждой партиции будет примерно одинаковое количество данных.

> Код: функция `hash_choose_num_partitions`

Собственно эта логика и используется внутри функции `hash_choose_num_partitions`.

Вначале мы рассчитываем сколько мы хотим иметь партиций. Но эта логика немного сложнее, чем простое деление, так как мы должны накладывать различные ограничения, например, на количество партиций есть верхняя и нижняя границы.

На этой строке (`mem_wanted / spill_mem_limit`) мы и видим основную идею - рассчитывать размер партиции таким образом, чтобы каждая полностью умещалась в памяти.

К сожалению мы можем ошибиться и партиция не будет помещаться в памяти и мы должны быть к этому готовы.

Так как мы уже использовали какое-то количество бит и при этом все кортежи попали в одну и ту же партицию, то префиксы хэшей этих кортежей равны, поэтому их нет смысла рассматривать. При этом с каждым последующим сбросом длина этого общего префикса будет расти.

> Код: функция `hashagg_spill_init`, где расчет маски

Чтобы уметь обрабатывать такие ситуации используется не простой префикс, а обобщенная битовая маска. Они рассчитываются на основании того сколько нам требуется партиций и сколько мы уже использовали. (`spill->mask = (npartitions - 1) << spill->shift`).

Если посмотреть на код, то увидим, что эта же функция используется и при повторном сбросе, но для расчета количества партиций необходимо знать количество групп.
Передавать значение, полученное от планировщика, нельзя, так как это совсем другая оценка.

> Слайд: HyperLogLog таблица и код, где добавляем его

Решение простое - мы будем сами это подсчитывать. Для этого используется структура данных HyperLogLog.
При каждом сбросе на диск мы будем ее обновлять и таким образом к моменту расчета количества партиций у нас на руках будет оценка этого количества.

Теперь на все вопросы мы ответили и можем рассмотреть как это происходит на самом деле.

> Код: `ExecAgg`

Как и всегда, мы начинаем с функции `ExecAgg`, но на этот раз наша стратегия хэширование и за нее отвечает `AGG_HASHED`.
Первое, что нужно сделать - заполнить хэш-таблицу.

> Код: `agg_fill_hash_table`

Этот код нам уже знаком: `fetch_input_tuple` - читаем кортеж и в `advance_aggregates` применяем функции перехода. Что они делают мы знаем.

Единственное, что отличается - промежуточный этап `lookup_hash_entries`. В ней и находится логика работы с хэш-таблицей.

> Код: `lookup_hash_entries`

Сразу встречаем структуру `AggStatePerHash` - она хранит состояние хэш-таблицы, а также все вспомогательные функции для нее, например, функция для хэширования кортежа.

> Слайд: представление хэш-таблицы + AggStatePerHash структура и от нее отходят стрелки к функции хэширования, таблице и т.д.

### Хэширование, сброс на диск

Но это самая легкая часть. Теперь нам нужно подумать о нехватке места, то есть как мы будем сбрасывать на диск.

И сразу вопрос - где и когда мы это обнаружим? Самое оптимальное - проверять тогда, когда мы память выделили, то есть после создания новой группы.

> Слайд: `initialize_hash_entry`

Эту функцию мы уже видели - она вызывается каждый раз, когда создается новая группа и это тот самый момент, когда мы можем выполнить проверку на переполнение памяти.

Перед тем как инициализировать агрегаты вызывается `hash_agg_check_limits`, которая это и проверяет.

> Слайд: `hash_agg_check_limits`

Проверка довольно тривиальная - сравниваем сколько выделили с пределом.
И когда эта проверка проходит, то мы переходим в режим сброса - `spill mode`.

> Слайд: `hash_agg_enter_spill_mode`

Этот `spill_mode` можно назвать другим режимом выполнения, так как меняется не только то, что мы сбрасываем кортежи на диск, но также и предположения о состоянии.

Во-первых, после обработки кортежа может получиться так, что для него нет памяти и мы не можем создать для него новую группу, поэтому необходимо добавить подобные проверки.

Одно из преимуществ, того, что мы компилируем выражения еще и в том, что мы, заранее зная какие будут значения переменных, можем изменить логику функции. И здесь эта идея накладывается превосходно.

> Слайд: `lookup_hash_entries` часть с `pergroup[setno] = NULL`

Помните часть, где мы выставляли указатель на `PerGroupState`? Теперь, т.к. этой группы нет, то нет и состояния, соответственно, мы передаем туда `NULL`.
Но если у нас все помещается в памяти, то мы можем гарантировать, что никаких `NULL` там нет.

> Слайд: `hash_agg_enter_spill_mode` выделен `agg_recomile_expressions`

У каждого выражения функции перехода есть 2 версии: с и без `NULL` проверки.
Вначале мы используем без проверки для большей производительности, но как только мы входим в spill режим, то создаем новую версию с этой проверкой.

> Слайд: `ExecBuildAggTransCall`

Если спустимся по колстеку, то дойдем до `ExecBuildAggTransCall` и первой командой, которую она добавляет и является эта самая проверка на `NULL`.

Таким образом, на мы храним 2 типа выражений - без проверки на `NULL` и с проверкой на `NULL`. И прямо сейчас мы собираем новое выражение, которое будет проверять этот `NULL`.

> Слайд: `hash_agg_enter_spill_mode` выделен `LogicalTapeSetCreate`

Далее, нам нужно подготовить место для сброса кортежей.
Для этой цели используется такая абстракция как `LogicalTapeSet` - множество `LogicalTape`, логических файлов, в которые мы будем записывать кортежи.
Создаем по одному `LogicalTape` на партицию.

> Слайд: архитектура LogicalTape и как они переиспользуются

Сам `LogicalTapeSet` - это всего-лишь удобная обертка над одним временным файлом, которая позволяет разделять его на несколько независимых виртульных файлов.
Но интересна идея за ним - многие паттерны работы очень похожи:

1. Последовательно записываем на диск что-то
2. Затем полностью это считываем, без необходимость повторного чтения

Этот паттерн работы также используется и при работе с партициями, поэтому для этих случаев сделана небольшая оптимизация - после того, как мы прочитали какой-то блок данных из тейпа, то этот блок возвращается в пул свободных и другие тейпы могут его затем переиспользовать.

На слайде можете видеть пример - изначально в нашем файле было 2 партиции. Но затем мы начали читать из первой. После прочтения первой страницы она была освобождена. Но в процессе выполнения мы понял, что ошиблись с оценкой и пришлось выполнить сброс на диск еще раз - это 3-я партиция. И вместо увеличения файла для записи новой страницы в конец мы переиспользуем освободившуюся страницу.

> Слайд: `hashagg_enter_spill_mode` выделен `hashagg_spill_init`

И последняя часть - инициализируем все партиции.
Чтобы централизованно все отслеживать используется отдельная структура `HashAggSpill`. В ней хранится вся информация по каждой партции.

Так как это наш первый сброс, то при инициализации статистику мы берем от планировщика - `numGroups` количество групп, а `0` - это количество использованных битов хэша (пока не использовали).

Внутри мы вызываем оцениваем количество партиций, которое нам потребуется и для каждой создаем свою партицию, в которую будем сбрасывать кортежи.

Подытоживая, spill mode означает следующее:

1. Перекомпиляций функций перехода с проверкой `NULL`
2. Создание временного файла для сброса кортежей
3. Подсчет статистики для каждой партиции

> Слайд: `lookup_hash_entries` выделен `p_isnew`

Теперь, когда мы получим следующий кортеж, то его не окажется в хэш-таблице и мы вынуждены будем его сбросить на диск.

Но разница в работе начнется не сейчас, а на следующей итерации, когда нужно получить группу для очередного кортежа.

Вначале мы натыкаемся на такую странную строку - `p_isnew = ...`. Задумка следующая: мы решаем можно ли создавать новый элемент в хэш-таблице, если его нет, но если это можно, то нам нужно знать нужно ли инициализировать состояние.

Таким образом, использование указателя решает эти 2 задачи одновременно: при `NULL` мы выполняем обычный поиск, а иначе нам позволено сразу создать новый элемент.

> Слайд: `lookup_hash_entries` выделен `spill_tuple`

Теперь же при поиске элемента мы можем получить `NULL` и тогда нам нужно сбросить этот кортеж.
И эта часть довольно интересна.

> Слайд: `SELECT a FROM tbl GROUP BY a` где SeqScan много атрибутов возвращает

```sql
EXPLAIN (VERBOSE) SELECT a FROM tbl GROUP BY a;
                           QUERY PLAN                           
----------------------------------------------------------------
 HashAggregate  (cost=1.05..1.08 rows=3 width=4)
   Output: a
   Group Key: tbl.a
   ->  Seq Scan on public.tbl  (cost=0.00..1.04 rows=4 width=4)
         Output: a, b, c
(5 rows)
```

Во-первых, если посмотреть на реализацию узлов плана, то заметим, что нижние узлы скана возвращают все атрибуты.
Если вы видели `EXPLAIN VERBOSE` вывод, то знаете, что всякие `SeqScan` узлы отдают все атрибуты, а не только те, которые нужны, но при этом нам может быть необходима только их часть.

> Слайд: `hashagg_spill_tuple` выделен `if (!aggstate->all_cols_needed)`

Поэтому при записи на диск мы оставляем только те атрибуты, которые действительно требуются.
А чтобы не сломать существующий код и не писать лишних проверок мы просто помечаем лишние атрибуты `NULL`.

> Слайд: `addHyperLogLog`

Во-вторых, не забываем обновить статистику - HyperLogLog, количество кортежей.
Но не забываем, что так как все кортежи идут в эту партицию, то какой-то префикс их хэша равен одинаковый, поэтому мы еще раз вычисляем хэш для хэша, чтобы сделать распределение более равномерным.

> Слайд: `LogicalTapeWrite`

И в-третьих, чтобы лишний раз не рассчитывать хэш-значение мы записываем и его прямо перед самим кортежом.

> Слайд: `lookup_hash_entries`

Кортеж сбросили на диск и теперь осталось только выставить `NULL`, чтобы поменить, что функцию перехода применять не нужно.

По окончании входа мы завершаем работу. Когда мы рассматривали in-memory only логику, то простили одну функцию - `hashagg_finish_initial_spills`.
Она занимается тем, что запечатывает все произошедшие сбросы на диск и подготавливает их для последующей обработки.

> Слайд: `hashagg_spill_finish`

Когда мы сбрасывали на диск, то использовали структуру `HashAggSpill`, но для перезаполнения хэш-таблицы использовать ее снова не самая лучшая идея.

На это есть несколько причин, например, во время работы нам уже не нужно состояние HyperLogLog - нам нужно уже получить готовое значение кардинальности.
Кроме этого, некоторые партиции могут оказаться пустыми и их бесполезно будет дальше обрабатывать.

Для решения этих проблем сейчас мы для каждую партицию запечатываем - для каждой создаем создаем свою отдельную структуру `HashAggBatch` уже готовую к использованию: статистика подсчитана, LogicalTape готов к чтению.

После этого полученный батч мы записываем в очередь, из которой будем в последствии читать и заполнять хэш-таблицу.

> Слайд: архитектура disk-spill обработки (`hash-agg-arch`)

Общая картина выглядит следующим образом:

1. На вход нам подается кортеж, для которого мы рассчитываем хэш
2. Если место есть, то записываем в хэш-таблицу, из которой в конечном счете он подастся на вход другому узлу.
3. В противном случае, мы идем по правой ветке
4. Для хэш-таблицы создается свой HashAggSpill, в котором хранятся партиции
5. В конце для каждой партиции создается свой HashAggBatch, который кладется в очередь
6. Каждый AggBatch указывает куда-то во временный файл, в котором хранятся его кортежи
7. Затем поочередно мы из очереди получаем батч и заполняем хэш-таблицу повторяя процесс

Можно сразу обнаружить крайний случай, когда каждый кортеж больше ограничения памяти work_mem даже с учетом hash_mem_multiplier. Но это также учтено - использование памяти мы проверяем после заполнения хэш-таблицы, поэтому потихонечку/помаленечку будем делать прогресс.

Но эта схема отображает общую идею, а не реализацию. Как минимум потому что в реализации код обработки кортежей из входа и из батча отличаются.

Для того, чтобы выполнить изначальное заполнение хэш-таблицы используется `agg_fill_hash_table`, но для обработки батчей - `agg_refill_hash_table`.

> Слайд: `agg_refill_hash_table`

Код внутри практически идентичен тому, что в `agg_fill_hash_table` за исключениями, что уже оговорили:

1. Чтение кортежей происходит из партиции, созданного тейпа для партиции
   > Слайд: `hashagg_batch_read`

2. При получении элемента хэш-таблицы мы сразу передаем хэш-значение, без его вычисления
   > Слайд: строка с `LookupTupleHashEntryHash` стрелка от `hashagg_batch_read(&hash)`

> Слайд: `agg_refill_hash_table`, строка с `hashagg_spill_init` выделить `batch->used_bits`, `batch->input_card`.

Также отличается код инициирования спила. Теперь нам нужно учитывать новую статистику по этой партции.
Эту информацию мы знаем на этапе создания `HashAggBatch`.

`AGG_SORTED` представляет стратегию сортировки и как можете заметить, плоская группировка выполняет тот же самый код.
И если так подумать, то действительно - плоская группировка это вырожденный случай сортировки, когда все кортежи как бы равны.

> Слайд: `agg_retrieve_direct`

Что происходит внутри `agg_retrieve_direct` мы уже видели, поэтому сконцентрируемся на основном различии - отличии разных групп.
А заключается она вот в этой строчке:

> Слайд: `if (node->aggstrategy != AGG_PLAIN)`

Когда мы прочитали очередной кортеж, то нам нужно проверить, что мы не достигли конца группы.
Если так, то просто прерываем цикл и вызываем финализатор.

Для проверки равенства вызываются обычные функции проверки. Получаем мы их из системного каталога.

И как обычно вызываем их не напрямую, а с помощью последовательности команд.

Но и тут не без замечаний, а именно замечание по семантике сравнения.
Мы работаем с SQL, который позволяет значению быть `NULL` и для него определены отдельные правила сравнения.
Если заглянем в системный каталог, то обнаружим, что основные функции сравнения помечены STRICT, то есть если хоть 1 из аргументов NULL, то мы их должны будем определить как неравные.
Но если вы запускали GROUP BY с NULL атрибутами, то замечали, что все NULL в этом случае равны.

> Слайд: `EEOP_NOT_DISTINCT` как выполняется

На самом деле для сравнения используется конструкция `IS NOT DISTINCT FROM`, которая имеет правила сравнения с NULL и возвращает `true` если оба операнда `NULL` и false если только 1 из них.
И обычный компаратор вызывается если оба операнда нормальные.

## Сложные аналитические функции: GROUPING SET, CUBE, ROLLUP

> Слайд: GROUPING SETS, CUBE, ROLLUP и примеры каждого

```sql
EXPLAIN SELECT a, b, c FROM tbl GROUP BY GROUPING SETS(a, (b, d), ROLLUP(a, b, c));
                        QUERY PLAN                        
----------------------------------------------------------
 MixedAggregate
   Hash Key: a, b, c
   Hash Key: a, b
   Hash Key: a
   Hash Key: a
   Hash Key: b, d
   Group Key: ()
   ->  Seq Scan on tbl
```

Для аналитических задач стандарт SQL определяет специальные функции: GROUPING SETS, CUBE и ROLLUP.
Идея в том, что мы одним выражением можем определить сразу несколько группировок по разным атрибутам, вместо того, чтобы писать несколько запросов и затем объединять их результаты.

Самый простой - это GROUPING SETS. Он определяет список выражений, по которым поочередно будет производиться группировка.

> Слайд: запрос внизу

Для наглядности в документации PostgreSQL приводится такой пример: находим общую сумму продаж по бренду и размеру (каждого в отдельности) и общие продажи.

```sql
SELECT brand, size, sum(sales)
   FROM items_sold
   GROUP BY GROUPING SETS ((brand), (size), ());

 brand | size | sum
-------+------+-----
 Foo   |      |  30
 Bar   |      |  20
       | L    |  15
       | M    |  35
       |      |  50
```

### Хэширование GS

> Слайд: запрос с EXPLAIN и от него стрелки к разным хэш-таблицам идут

```sql
EXPLAIN SELECT a, b FROM tbl
   GROUP BY GROUPING SETS((a, b), c, (c, d));

                        QUERY PLAN                        
----------------------------------------------------------
 HashAggregate  (cost=1.06..1.19 rows=10 width=16)
   Hash Key: c, d
   Hash Key: c
   Hash Key: a, b
   ->  Seq Scan on tbl  (cost=0.00..1.04 rows=4 width=16)
(5 rows)
```

Для него все просто - у нас на руках имеется множество отдельных атрибутов группировки.
Так как мы умеем работать с 1 группой, то для каждой GROUPING SETS создадим свою хэш-таблицу и будем работать с каждой по отдельности.

> Слайд: `lookup_hash_entries` с ->num_hashes (+ и другие для наглядности показать)

На этой слайде можете видеть общую идею поддержки множества GROUPING SETS.
Все структуры для каждого GROUPING SET мы храним в большом массиве, проиндексированном номером этого GROUPING SET.
Затем в цикле проходим по всем и обрабатываем каждый отдельно.

Для хэширования в переменной `num_hashes` хранится количество этих самых хэш-таблиц для каждого GROUPING SETS.
Если GROUPING SETS нет, то он просто равен 1.
При этом в таких циклах итерационная переменная называется `setno`.

> Слайд: `hashagg_finish_initial_spills`

Например, когда запечатываем сброшенные партиции, то делаем это для каждой хэш-таблицы

> Слайд: `hash_agg_enter_spill_mode`

Когда мы входим в spill режим, то `HashAggSpill` создается для каждой хэш-таблицы.

### Сортировка GS

> Слайд: запрос с ROLLUP

```sql
SELECT a, b, c FROM tbl GROUP BY ROLLUP(a, b, c);

GROUPING SETS(
   (a, b, c),
   (a, b   ),
   (a      ),
   (       )
)

                           QUERY PLAN                           
----------------------------------------------------------------
 GroupAggregate  (cost=1.08..1.22 rows=10 width=12)
   Group Key: a, b, c
   Group Key: a, b
   Group Key: a
   Group Key: ()
   ->  Sort  (cost=1.08..1.09 rows=4 width=12)
         Sort Key: a, b, c
         ->  Seq Scan on tbl  (cost=0.00..1.04 rows=4 width=12)
(8 rows)
```

Группировка хэшированием хороша, так как мы можем параллельно обрабатывать несколько групп за раз.
Но в случае с сортировкой такой трюк не прокатит, т.к. разные GROUPING SETS могут иметь разные атрибуты группировки.

Но все же мы можем применить оптимизацию. Чтобы понять какую посмотрим на структуру ROLLUP. Он разворачивается в несколько GROUPING SETS, каждый раз удаляя по 1 атрибуту с конца.

Первое наблюдение - вся эта последовательность может быть отсортирована 1 раз по наибольшей группе, а все остальные будут также отсортированы, т.к. это префиксы сортированной последовательности.

> Слайд: `gs-group-sort-idea`

Если мы вручную попытаемся разметить границы каждого GROUPING SET, то увидим закономерность.

Пронумеруем наши GROUPING SET, по их размеру, т.е. группу a, b, c - это 3, а a - 1, то можем сделать второе наблюдение - когда изменяется N-ый атрибут, то это означает конец группы для N-ого GROUPING SET'а, а также всех больших размером.
Например, когда мы доходим до `1 2 1`, то изменяется атрибут под номером 2 и мы финализируем группы `1, 1, 2` и `1, 1`.

Аналогично, когда встречаем `2, 2, 1`, то изменился атрибут под номером 1, поэтому мы финализируем `1, 2, 1`, `1, 2` и `1`.

В этом и заключается идея оптимизации - находить подобные структуры и обрабатывать несколько групп за 1 проход сортировки.

> Слайд: запрос снизу + выделить Sort, он один

Например, в этом запросе группы в GROUPING SETS не напрямую отображаются в ROLLUP, но планировщик все-таки нашел эту структуру:

```sql
EXPLAIN SELECT a, b, c FROM tbl GROUP BY GROUPING SETS (
   (c, b, a),
   (b, a),
   (a)
);
                           QUERY PLAN                           
----------------------------------------------------------------
 GroupAggregate  (cost=1.08..1.21 rows=9 width=12)
   Group Key: a, b, c
   Group Key: a, b
   Group Key: a
   ->  Sort  (cost=1.08..1.09 rows=4 width=12)
         Sort Key: a, b, c
         ->  Seq Scan on tbl  (cost=0.00..1.04 rows=4 width=12)
(7 rows)
```

> Слайд: `agg_retrieve_direct` из прошлых слайдов - сохранение grp_firsttuple

Если посмотрим внутрь еще раз, то в том цикле обработки кортежей мы ничего о GROUPING SETS не найдем - ни обнуружение их границ, ни даже сравнение префиксов - мы всегда сравнивали кортежи полностью.

Дело в том, что из 2-ух предыдущих выводов можно сделать еще 3-ий - как только мы достигли кортежа не равному нашему, то финализируем все группы до первой с одинаковым префиксом.
Но наша модель выполнения - итераторная - возвращаем по 1 кортежу за вызов, поэтому этот последний неравный надо где-то сохранять - что мы и делаем по нахождении этого неравного.

> Слайд: `agg_retrieve_direct` где `outertuple =` + выделить место `ExecQualAndReset` + только этот if показать и сразу в конце `finailize_aggregates`

Затем, когда нас вызывают еще раз мы проверяем очередной префикс и если есть неравные, то финализируем еще один GROUPING SET.
Вот таким образом мы обработаем несколько GROUPING SET за 1 проход в потоке.

> Слайд: запрос снизу + выделить все Sort Key, их 2

Но построить такую обработку мы можем не всегда.
Например в этом запросе такое провернуть не получится, поэтому для группировки по `c` мы вынуждены выполнить еще 1 сортироку:

```sql
EXPLAIN SELECT a, b, c FROM tbl GROUP BY GROUPING SETS (
   (b, a),
   (a),
   (c)
);
                           QUERY PLAN                           
----------------------------------------------------------------
 GroupAggregate  (cost=1.08..1.26 rows=9 width=12)
   Group Key: a, b
   Group Key: a
   Sort Key: c
     Group Key: c
   ->  Sort  (cost=1.08..1.09 rows=4 width=12)
         Sort Key: a, b
         ->  Seq Scan on tbl  (cost=0.00..1.04 rows=4 width=12)
(8 rows)
```

> Слайд: `agg_retrieve_direct` верхнеуровнево

Когда мы смотрели на код `agg_retrieve_direct`, то нам на вход уже подавались отсортированные кортежи и мы не думали откуда они приходят. Точнее, мы знали - из `fetch_input_tuple`, но внутрь не смотрели - теперь самое время.

> Слайд: `fetch_input_tuple`

Внизу мы видим вызов функции `ExecProcNode`. Это та функция, которая вызывает нижний узел и получает кортеж от него.
Когда мы выполняем обычный запрос, без GROUPING SET, то используется именно он.

Но вот, кроме нее стоит обратить внимание на 2 поля: `sort_in` и `sort_out`.

> Слайд: схема фаз выполнения с примером запроса и GROUPING SET'ами в каждой фазе (`gs-sort-sort_in-sort_out`)

Все выполнение разбито на отдельные этапы, которые называют фазами.
Каждая описывается структурой `AggStatePerPhase`.
В каждой фазе находится несколько GROUPING SET'ов, но таких которые мы можем обработать одновременно.

На слайде можете видеть уже более наглядный пример взаимосвязи фаз друг с другом.
И связующим звеном в этой истории являются эти 2 поля: `sort_in` и `sort_out`.

> Слайд: запрос внизу + EXPLAIN

Для такой махины наш запрос должен выглядеть примерно так:

```sql
EXPLAIN SELECT a, b, c, d, e, i, j, k FROM tbl1 GROUP BY GROUPING SETS(ROLLUP(a, b, c), ROLLUP(d, e), ROLLUP(i, j, k));
        QUERY PLAN                              
--------------------------
 GroupAggregate
   Group Key: d, e
   Group Key: d
   Group Key: ()
   Group Key: ()
   Group Key: ()
   Sort Key: a, b, c
     Group Key: a, b, c
     Group Key: a, b
     Group Key: a
   Sort Key: i, j, k
     Group Key: i, j, k
     Group Key: i, j
     Group Key: i
   ->  Sort
         Sort Key: d, e
         ->  Seq Scan on tbl1
(17 rows)
```

Для каждой фазы представлен свой Sort Key и внизу написаны их ключи группировки.

> Слайд: вперед, еще раз архитектуру на пред слайде которая

Если не учитывать порядок следования фаз, логика обработки идентичная.

> Слайд: `fetch_input_tuple` выделен sort_in

Через `sort_in` мы получаем кортежи от предыдущего этапа, причем они отсортированы в том, порядке, который нужен нам.

> Слайд: `fetch_input_tuple` выделен `sort_out`

После же чтения мы этот кортеж должны передать на следующий этап, для этого мы кладем его в `sort_out`. При переходе к следующему этапе выполняем сортировку и просто меняем sort_in и sort_out местами.

### MixedAggregate

Теперь мы знаем как можно обработать несколько GROUPING SETS разными стратегиями, а также как переделать множество вложенных и сложных GS/CUBE/ROLLUP в список из обычных GS.
Теперь мы в теории умеем обрабатывать любой запрос, но подход на выборе исключительной стратегии может дать плохой результат, то есть если мы выбираем либо хэширование, либо сортировку.

> Слайд: MixedAggregate и план с ним внизу

Для решения этой проблемы была придумана стратегия MixedAggregate. Ее идея в том, что мы можем объединить в 1 узле и хэширование, и сортировку, причем выбирать какая из стратегий будет выгоднее для каждой группы в отдельности.

Если мы посмотрим на план этого запроса, то увидим, что она из себя представляет.

```sql
CREATE TABLE tbl(a int, b int);
CREATE INDEX ON tbl(a, b);
INSERT INTO tbl VALUES (1, 1), (1, 2), (1, 3), (1, 4), (1, 5), (1, 6);
SET random_page_cost TO 0;

EXPLAIN SELECT a, b from tbl3 group by cube(a, b);
                                     QUERY PLAN                                     
------------------------------------------------------------------------------------
 MixedAggregate  (cost=0.13..0.41 rows=14 width=8)
   Hash Key: b
   Group Key: a, b
   Group Key: a
   Group Key: ()
   ->  Index Only Scan using tbl3_a_b_idx on tbl3  (cost=0.13..0.22 rows=6 width=8)
(6 rows)
```

Планировщик увидел, что у нас уже есть индекс с нужной сортировкой, но для последнего GROUPING SET он решил использовать хэширование.

> Слайд: `gs-sort-sort_in-sort_out`

Фазы для сортировки организованы просто как цепочка из GroupAggregate, передающая кортежи через sort_in/sort_out.

> Слайд: фаза хэширования единственная (`gs-hash-phase`)

И в такой архитектуре хэширование описывается единственным узлом, так как он может обработать вообще все GROUPING SET за раз.

Но в MixedAggregate используется как сортировка так и хэширования. Остается вопрос - как это все скомбинировать? Фаза хэширования одна, поэтому надо решить куда вставить ее.

Если делать ее расположение динамическим, то появится много кода обработки и он станет читаемым еще хуже.

В начало не вариант, так как на вход могут подаваться уже отсортированные данные, поэтому нам придется выполнять сортировку еще раз.

Куда-то в между фазами сортировки тоже не лучшая затея, так как все передается через сортировку, а хэшированию она не нужна.

Остается последний вариант - вставить в конец. Но опять вспоминаем - все передается через сортировку, но нам она не нужна.

Решение этой проблемы элегантное - мы разделяем логику работу хэширования на 2 части: изначальное заполнение таблицы и чтение из нее.

> Слайд: `agg_retrieve_direct` с `== AGG_MIXED && current_phase == 1`

Таблицу мы заполняем в самой первой фазе. Внутри `agg_retrieve_direct` мы одновременно обрабатываем и сортировку и хэширование.
Когда мы прочитали кортеж и видим, что на первой фазе смешанного агрегирования, дополнительно обрабатываем хэширование.
Напомню, что в `lookup_hash_entries` вынесена вся логика работы с хэш-таблицей - поиск элемента, его создание, запуск spill режима.

В конце фазы у нас на руках имеется заполненная хэш-таблица и, возможно, сброшенные партиции.

> Слайд: `ExecAgg` с разделением AGG_HASHED и AGG_MIXED

Когда мы доходим до последней фазы, то вместо `AGG_HASHED` там стоит `AGG_MIXED`, который пропускает этап заполнения таблицы и сразу начинает читать из нее.

> Слайд: `ExecAgg` выделен phase->

Как вы можете догадаться, нам нужно различать разные фазы друг от друга, но при этом понимать как у нас глобальная стратегия.

Поэтому у каждой фазы имеется своя отдельная стратегия, которой он придерживается.

> Слайд: схема MixedAggregate, этап 1

Таким образом мы пришли к полной картине обработки MixedAggregate.

В самом начале кортежи мы получаем из какого-то подузла. Этот вход мы передаем фазе AGG_SORTED и одновременно с этим заполняем хэш-таблицы.

> Слайд: схема MixedAggregate, этап 2

После этого обрабатываем каждый следующий AGG_SORTED как раньше, передавая кортежи через sort_in/sort_out.

> Слайд: схема MixedAggregate, этап 3

В самом конце мы приходим к AGG_HASHED. Хэш-таблица уже заполнена и нам остается только обработать ее.

На этом мы и закончим разбор архитектуры группировки и теперь подытожим.

> Слайд: несколько GROUP BY, стрелка вправо - в какие GS разворачиваются

GROUP BY на входе разбиваем на множество из отдельных GROUPING SET.

> Слайд: 2 столбца - AGG_SORT/AGG_HASHED и в каждом по выражениями (типа так и эффективнее реализовать)

Определяем какая стратегия подходит для них лучше всего.

> Слайд: agg_hashed

Eсли все эффективнее выполнить хэшированием, то для каждого GROUPING SET создаем свою хэш-таблицу и заполняем ее независимо от других.

Если память переполнена то инициируем spill режим и записываем кортежи, групп для которых нет, на диск в свои партиции.

Каждая партиция расчитывается таким образом, чтобы из нее можно было построить отдельную хэш-таблицу, которая бы полностью умещалась в памяти.

Записываем кортежи на диск, а после вставляем эту партицию в очередь на обработку.
Затем заново обрабатываем партицию и если необходимо еще раз сбрасываем кортежи и кладем новую партицию в очередь.
И так до тех пор пока не будет обработан каждый кортеж.

> Слайд: открыт столбец AGG_SORT

Если нужно сортировка, то все GROUPING SET разбиваем на отдельные подгруппы, которые можем обрабоать за 1 проход, грубо говоря, они имеют общий префикс.

> Слайд: схема sorted agg (была ранее)

Каждую такую фазу мы обрабатываем в потоке за один проход.

По море обработки каждого кортежа кладем его в sort_out. По окончании этот sort_out будет отсортирован и перед на вход другой фазе AGG_SORTED.

> Слайд: оба столбца открыты

Если эффективно использовать обе стратегии, то поступаем так.

> Слайд: схема с MixedAggregate (ранее была)

В начале располагаем стретегию сортировки, но на первой фазе мы заполняем хэш-таблицу.

Когда закончили с сортировкой, то начинаем фазу хэширования, но таблица уже заполнена, поэтому сразу переходим к логике ее обработки.

## Невошеднее

Вот так выглядит архитектура группировки в postgres, но это общий вид. Есть много деталей, оставшихся за бортом. О некоторых из них сейчас поговорим.
Первая - частичная агрегация.

### Частичная агрегация

Для того, чтобы добиться большей производительности часто используется параллелизация.
Мы запускаем фоновые воркеры, которые обрабатывают кусок своих данных, а затем соединяют результат вместе.

> Слайд: план с частичными агрегатами

У группировки и агрегации такое поведение также имеется и поддерживается с помощью частичной агрегации.
Это могли видеть, когда в плане были узлы с префиксом `Partial` и `Finalize`.

> Слайд: CREATE AGGREGATE с указанием combine func

Для того, чтобы это реализовать агрегаты должны дополнительно указать функцию `combine`.
Ее идея проста: к состоянию мы можем применить не отдельные кортежи, а уже другое состояние, т.е. батчем применим сразу множество кортежей.

Теперь несколько узлов могут независимо вычислить агрегат, а затем потом мы соединим их и получим готовое значение агрегата.

Но когда мы посмотрели на код, то не видели никаких упоминаний о combine функциях, только вызов функции перехода.
И в этом заключается идея - мы работаем в кортежами и читаем из них атрибуты, которые передаем какой-то функции, которая возвращает состояние агрегата.
В такой постановке задачи мы можем передавать состояние агрегата как обычный атрибут, а вместо функции перехода вызывать функцию комбинирования.

> Слайд: 3806 `if (DO_AGGSPLIT_SKIP_FINAL)` + `finalize_aggregate` else ветка

В partial узле мы работаем с нормальными кортежами и атрибутами, но finalize мы сейчас не вызываем, поэтому просто убираем его и возвращаем сырое значение.

> Код: 3948 `transfn_oid = agg_form->aggcombinefn`

А вот в finalize нам на входе передаются уже состояния агрегата, поэтому мы используем combine функцию, вместо transition.

### ordered set/distinct

> Слайд: запрос для ordered set aggregate

Вторая деталь - это особый класс агрегатных функций - ordered-set aggregate.

Их отличительная деталь в том, что для вычисления им нужно получить отсортированный вход.
Например, моду (`mode`) нельзя вычислить в потоке, нужно знать всю выборку.

> Слайд: хэш-таблицы с группами и у каждого свой массив

Как вы заметили в стратегии хэширования мы одновременно обрабатываем несколько групп, а не как сортировка по одной.
Из-за этого мы должны отслеживать переполнение памяти. Но если мы наивно для каждой группы будем хранить ее массив кортежей, то возникнет 3 проблемы.

Первое - переполнение надо будет проверять после каждого кортежа, а не только при создании новой группы, так как этот кортеж легко может быть записан в этот массив.

Второе - где хранить этот массив. Размер всего состояния 10 байт, но еще один указатель добавит 8 байт, то есть в этой хэш-таблице мы сможем хранить почти в 2 раза меньше элементов. Хотя подавляющая часть агрегатов этого не требует. Спотыкаемся на ровном месте.

Третье - нам придется думать как быть, если мы в spill режиме (памяти больше нет), но кортеж должны сохранить для дальнейшей сортировки. В текущем коде отслеживанием занятой памяти ведется для каждого `tuplesort` независимо. Это значит, что придется добавить еще больше кода, который скорее всего кроме нас никто использовать не будет.

> Слайд: сортировка и для каждого агрегата свой массив

Поэтому принято решение при обнаружении подобных агрегатов не использовать хэширование, то есть только сортировка.
И с ней все гораздо проще, так как одновременно мы обрабатываем только по 1 группе в каждом GROUPING SET.
Это значит, что для каждого агрегата мы будем хранить свой массив, который во время финализации отсоритруем и применим функцию перехода.

> Слайд: `initialize_aggregate` с инициализацией

Для каждого ORDERED SET агрегата мы храним массив индексированный по номеру GROUPING SET.

> Слайд: `ExecEvalAggOrderedTransTuple`, `EEOP_AGG_ORDERED_TRANS_TUPLE`

Затем каждый кортеж мы будем класть в его собственный `tuplesort`.
И опять-таки для этого есть своя отдельная функция и свой opcode.

> Слайд: `finalize_aggregates` где `process_ordered_aggregate_single`

В него по мере чтения будут добавляться кортежи, которые мы затем отсортируем и передадим функции перехода.
Но в остальном это такие же агрегатные функции - transition, finalize, combine.
